### 决策 17：动态码采用「二维码 + 6 位口令」双通道（落实决策 13 的兜底）

- 选择：班干部端**同时出示真二维码与 6 位数字口令**；教师端既能「扫码发起」（`wx.scanCode`）也能「输入口令」发起。后端 `/code/generate` 增加返回 `code`(6 位口令) 与 `qrPayload`(`kcsq://code/<codeId>`)；`/code/verify` 支持 `{qrContent}|{code}|{codeId}` 三选一
- 原因：落实决策 13"保留手动刷新按钮与口令兜底"；弱网/光线差时扫码不便，口令可兜底；且**二维码由小程序端本地绘制**（纯 JS 编码器），扫码用 `wx.scanCode` 本地能力，**均不需要备案域名**，当前阶段即可联调
- 备选方案：仅二维码（需教师扫码，弱网体验差）；仅 6 位口令（少了一键发起的便利）；由服务端生成二维码图片（后端需引依赖，且要域名）
- 费用或审核风险：6 位口令仅在**当前有效未消费**的码中唯一（并发量大时可能重试）；口令属短码，防猜测依赖 60 秒有效期 + 一次性消费；二维码为明文载荷，防伪造仍由服务端 HMAC 签名与库内校验保证
- 用户确认：已确认
- 确认日期：2026-09-27

### 决策 18：业务流程简化为「班干部驱动 + 教师扫码确认」（覆盖决策 4 的发起方向）

- 选择：
  - **班干部（学委）**录入**班级课程清单**（课程名 + 授课老师 + 节次/地点/学时），**录入一次长期保留**，后续上课自动带出、无需重复录入
  - 每次上课由班干部**发起课时会话**并出示**动态二维码（A 码 + B 6 位口令）**
  - **任课老师只需扫码（或输口令）→ 看到本次课时信息 → 点一下「确认」**即完成；**不再填表、不再手写签名**
  - 支持对本次课**临时调整**（改实际授课人/节次/地点），**不需要审批**
  - 学时按**学生端录入的实际授课人**归属统计
  - **取消**：调课记录、停课记录、教务处审批层
- 原因：用户明确要求简化——"学生编辑端就可以编辑，不需要通过教务处这一层面，让流程复杂化"；教师侧操作降到最低（扫一下 + 点确认）
- 备选方案：保留"教师填表发起 + 班干部手写签名 + 院系管理员审补签"的旧流程（已保留接口，历史数据与旧客户端可用）
- 费用或审核风险：学时归属依赖学委如实录入；以**动态码 60 秒一次性**（防截图代签）、**确认人身份留痕**、**确认人姓名与实际授课人不符标记**（`confirmNameMismatch`，后台可筛）与**审计哈希链**共同约束；不引入定位
- 用户确认：已确认
- 确认日期：2026-09-27

### 决策 19：支持小程序自助解绑 / 换绑

- 选择：在小程序内提供两条自助解绑通道——
  1. **本人解绑**（已登录）：`POST /auth/unbind`，解除当前微信与工号的绑定
  2. **换微信自救**（未登录）：`POST /auth/unbind-self`，用工号/学号 + 姓名（白名单校验）解绑
  - 两道频率限制：同一工号 24h ≤ 2 次、同一 IP 1h ≤ 5 次（失败尝试同样计数）；全部写审计留痕
  - 解绑使 `auth_epoch + 1`，该工号此前签发的所有令牌立即失效（含旧微信手里未过期的 token）
  - **解绑只解除绑定关系，任何历史课时/统计/审计数据一行不动**
- 原因：用户提出"老师换微信要能自己换绑，不必每次都找教务处"；在便利与安全之间取频率限制 + 审计 + 弱凭证披露的折中
- 备选方案：仅教务处后台人工解绑（最安全但麻烦）；叠加短信验证码 / 学校统一认证（更安全，本期待实现基础设施）
- 费用或审核风险：**弱凭证风险**——工号常出现在课表公示、姓名非秘密，知道二者的人可解绑他人微信；缓解措施为姓名严格校验 + 频率限制（盲猜成本高）+ 两种失败同提示（防工号枚举）+ 全链路审计 + `auth_epoch` 令牌失效。生产环境建议再叠加短信/统一认证与网关级限流
- 用户确认：已确认
- 确认日期：2026-09-27
